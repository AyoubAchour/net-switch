# M4: native service contracts, first part

2026-10-22. This is the first reviewable part of the native-contracts PR in the M4 plan. Control's production cutover is still separate.

## Scope

The `m4_native` build uses the native runtime through the installed `netswitch-engine service` entrypoint and Ctl cleanup. Ordinary builds retain the M2 stand-in until the Control cutover. Selection is compile-time; there is no runtime fallback. The temporary tag goes away at cutover.

The native service shares runtime construction, authenticated transport and cleanup with standalone acceptance. Native ownership locks remain the exclusion boundary. The service supplies readiness and resume notifications and serializes epoch/revision history into one durable record. A restarted engine reports no loaded revision until start; an in-progress start does not report a loaded policy before capture succeeds. Old stand-in state is rejected here, pending the separately reviewed migration.

SCM and command exits retain the direct native outcome: clean adapter loss is 3, ordinary failure is 1, and an unrecovered Go panic remains 2. Joined cleanup errors cannot inherit the clean-loss code. Service status exposes the main exit separately from the final outcome. A final clean outcome requires a matching successful recovery result; a recovery failure becomes failure 1. Recovery captures the instance under the same native ownership lock, then writes its result after all closes, including the lock release. Each instance has its own outcome file, so an old recovery cannot overwrite a replacement service's result. A terminal message is still provisional: Control's terminal handling and restart budget belong to the cutover.

Native history uses one atomic replacement with file and directory sync, without an unread backup. After a failed sync following replacement, the next operation preserves the durable epoch/revision floor. An unacknowledged epoch may be retried, but an acknowledged epoch cannot be reused. Status publishes adapter loss as stopping immediately, includes a bounded last error, and retains failures until a new start.

A temporary-file regression also reproduced Windows replacement failing while a status reader holds the destination open, including with delete sharing. Native state replacement retries only sharing/access conflicts for at most 250 ms; permanent errors still fail. The journal observer never repairs or writes the journal and waits for the final recovery result before reading its checkpoint, so the diagnostic cannot block or truncate the cleanup it measures.

## Totals

The maximum-cardinality test admits and closes 65,536 distinct 512-byte app identities across 255 lines. The old single reply exceeds 1 MiB by more than thirty times. This is measured from real flow-table accounting, with no fabricated oversized diagnostic field.

`totals {cursor}` now returns `{engineInstanceId, apps, lines, count, receipt, cursor?}`. Each counter includes `{up, down, generation}` and is cumulative within that generation. Pages use a 512 KiB encoded budget, including space for escaping and the reply envelope. The first call freezes the counters, including closed flows; later pages read that same snapshot. `count` is the total number of app and line entries. A missing cursor means completion. Both existing native acceptance clients consume and validate the full sequence. The 65,536-app/255-line fixture now takes 70 pages; its largest measured reply is 523,543 bytes.

Totals share the flow snapshots' four-slot, ten-second and byte reservations. Aggregation memory is reserved before copying. A completed snapshot remains reserved until acknowledgement or expiry. An exhausted snapshot budget or expired cursor is an error; no accounting is truncated or evicted. A caller must discard an incomplete poll. `stats` remains separate and bounded.

The retained set is capped at 65,536 app identities and 65,536 line identities. After consuming every page, Control must durably commit its per-instance, per-generation byte high-water marks, then send fenced `ackTotals {opId, receipt}`. Acknowledgement retires only idle entries whose generation and byte values still match the snapshot. Configured lines retain their cumulative counters; retired lines can be removed. New traffic, partial reads, expired/foreign receipts and late overlapping acknowledgements cannot discard unread bytes. A repeated identity receives a new generation after retirement. A lost acknowledgement is retried with the same operation ID; if it expired, another full read is safe because Control has already committed its high-water marks.

If Control falls behind and fills the retained set, existing identities keep forwarding. Admission of a new identity is refused with the separate accounting-capacity counter until space is acknowledged. This is the bounded, exact-accounting contract to record in the spec; the production Control consumer belongs to the cutover. The acceptance clients consume in memory because they are test controllers, not durable usage stores.

Tests cover maximum cardinality, escaped IDs, completed-between-poll traffic, a flow closing after the first page, concurrent new traffic, partial/expired/foreign reads, overlapping acknowledgements, both TCP and UDP admission, line churn, shared snapshot budgets and controller fencing. A long churn test consumes all bytes from 102,400 distinct 512-byte identities with a retained limit of 1,024, without resetting the table. It checks exact independently generated bytes and live heap after forced GC: 244,768-byte baseline and 413,432-byte peak in the local run. Hosted fault builds separately fill both retained identity sets to 65,536 and time a complete read over the installed service connection while a held flow continues. That measurement must finish inside the unchanged ten-second snapshot lifetime.

## Installed service proof

`native-service-contracts.yml` runs Windows x64/ARM64, Ubuntu 24.04 x64/ARM64 and Ubuntu 26.04 x64. Each job builds and installs two native candidates in separate directories: one without fault hooks and one with `lifecycle_test`.

The suite records each binary's version/hash, checks the running service image and PID, and uses the real root/SYSTEM engine connection. It also verifies that another OS user is denied while the engine service is live. Tests exercise start/apply/status, stale/conflicting revisions, stable apply points, reattachment/fencing, old-flow closure with newer-flow survival, all totals pages, historical state after restart, graceful stop, lease expiry, actual service crashes and native Ctl/SCM/ExecStopPost cleanup. Capture and held traffic are established before any cleanup is credited.

Windows asserts the journal's persistent WFP sublayer and three filters exist before killing the service, then waits for their removal and journal retirement. The explicit Ctl case disables automatic recovery, kills the service, proves those leftovers still exist, and only then runs cleanup. Linux proves its journaled selection rules similarly. A crash reported as clean 0 or adapter loss 3 fails. Separate injected exit-3 cases pass through the real manager, with both successful recovery and a recorded recovery failure.

The build without fault hooks is given an arm file and must continue forwarding without producing a hit record. The installed fault build has two observations:

- **Forwarding-only stall:** stop the real TUN read pump after it receives a packet. Require blocked traffic for at least 22 seconds while renewal/version rounds still answer within three seconds. Verify capture still exists, release the fault, and verify the same stream resumes.
- **Whole-service stall:** suspend the actual service process. Require its held stream and IPC to stop answering while SCM/systemd still reports that same process running, for more than the 30-second lease. Verify capture still exists. Resume without sending renewals and require lease cleanup and direct traffic to recover.

These tests record `M4_STALL` evidence and `M4_PROGRESS` stats before, during and after the read-pump stall. This injection observes the read-pump domain only; it does not prove write-path or network-stack stall detection. The whole-service case records the last available counters and that stats become unavailable while suspended. These are observations, not a watchdog detector or a claim that native recovery already meets M2's guarantee. The coordinator reviews the hosted results before detector design. A separate watchdog process requires an architecture decision before implementation.

## First hosted failures and diagnosis

In run 39843807971, Linux ARM attached at 20:01:55 UTC; systemd deactivated the engine successfully at 20:02:26. The denial probe did not run until 20:02:36. Creating its OS user took longer than the 30-second lease, and this test client had no renewal loop. Ubuntu 26.04 x64 reproduced the same failure. The harness now renews while attached, stops and joins that loop before fencing/stop/suspension, and leaves the other-user denial requirement unchanged.

Windows was already ready: focused hosted diagnostic run 39847601708 recorded `ready-callback-end` at 20:29:21.682 UTC. Its epoch stayed zero because hello never completed. The shared M2 IPC dialer writes an impersonation primer byte before JSON; the native transport authenticates the SYSTEM process directly and does not consume that byte. The native decoder rejected it, then the RPC reader discarded the uncorrelated error and waited for the six-minute test deadline. A pure regression reproduced that misleading timeout before the fix. Native dialing now omits the M2 primer while retaining the SCM process check, and RPC surfaces a protocol rejection immediately. Attach has a specific ten-second diagnostic deadline, with service startup/outcome evidence on failure. Teardown explicitly stops the native service before uninstalling it.

## ARM stall result and further measurement

At head `886b220a`, run 39856819110, Windows ARM job 120097049942 passed the product build and both real cleanup paths. The fault build read all 131,072 accounting entries in 83 pages in 755.9 ms. Both exit-3 cases passed: `Cleanup:failed` with `hosted recovery failure before OS cleanup` belongs to the intentionally failing recovery case, not an unexpected cleanup failure.

The read-pump stall failed after 21.58 s with Winsock error 10060 (`WSAETIMEDOUT`). Whole-process suspension failed after 23.60 s, including the two-second IPC timeout before sending data. Those are native socket failures, not Go's `os.ErrDeadlineExceeded` polling errors. The old observation returned immediately and therefore proved neither survival through the full windows nor the post-fault fate of those streams. It did not complete the 35-second whole-service observation. The approximately equal times after sending data point to retransmission exhaustion, but the old log has no client retransmission counts or actual socket settings to prove that cause.

The additional diagnostic keeps flow loss a test failure and continues collecting evidence through 22/35 seconds and release/cleanup. A separate 35-second quiet-stream control exercises the same one-second read deadlines with forwarding live. Windows reads the real client's keepalive, send/receive timeout and retransmission settings without changing them; `SIO_TCP_INFO` samples established state, unacknowledged bytes, retransmitted bytes and timeout episodes. Query cost is measured before injecting the fault, and sampling is every five seconds plus fault transitions, not per packet. Linux's Unix relay is explicitly labelled as such, not represented as the namespace TCP socket.

`M4_FLOW` records the first non-deadline error with elapsed time and errno, the same stream after release, and an independent fresh-stream probe. A successful fresh connection cannot turn an old-stream failure green. No TCP settings, stall duration, lease limit or failure threshold is increased. The detector and process model remain unchanged while these observations are gathered.

## Linux installed-service sysctl boundary

The installed unit correctly made `/proc/sys` read-only. The native engine nevertheless unconditionally wrote `disable_ipv6=0` for its newly created TUN; standalone acceptance had no such mount boundary. The native-only unit now keeps `ProtectKernelTunables=yes`, permits `/proc/sys/net/ipv6/conf`, and makes its `all`, `default` and `lo` subdirectories read-only again. Control and the stand-in unit receive no exception. The engine verifies the TUN's index/name/ownership alias, reads the current value and writes only when it inherited `1`.

This is the smallest static parent that can contain the runtime-created device. A narrower **existing** per-device file can be made writable, but our random per-instance path does not exist when systemd constructs the mount namespace. Without `-` startup fails; with `-` the missing mount is skipped, not added when the device appears. Both [systemd 255's path rules](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#ReadWritePaths=) and [259's rules](https://www.freedesktop.org/software/systemd/man/259/systemd.exec.html#ReadWritePaths=) support nested writable/read-only mounts. Their [255](https://github.com/systemd/systemd/blob/v255/src/core/namespace.c) and [259](https://github.com/systemd/systemd/blob/v259/src/core/namespace.c) implementations apply the `/proc/sys` protection as a mount and skip missing optional entries at setup. No extra capability, helper process or global sysctl change is introduced. The exception necessarily exposes other per-interface IPv6 knobs to Engine; global/default knobs, IPv4, sysfs and cgroups remain read-only. A per-device sandbox would require a different creation/hosting arrangement.

Avoiding the write is safe when the inherited value is already zero, which the engine now does. It is insufficient when a physical line has usable IPv6 but newly created devices inherit `disable_ipv6=1`. The kernel copies the namespace defaults into new IPv6 devices, and rejects disabled devices for IPv6 address configuration. The netlink IPv6 link setter accepts token/address-generation changes, not `IFLA_INET6_CONF` writes, in both [Linux 6.8](https://github.com/torvalds/linux/blob/v6.8/net/ipv6/addrconf.c) and [7.0](https://github.com/torvalds/linux/blob/v7.0/net/ipv6/addrconf.c). Raising the link or changing its address-generation mode therefore cannot replace this sysctl write.

Write-site audit: `enableIPv6` is the only product `/proc/sys` or sysfs writer in the native Linux engine. The engine reads `ping_group_range` and the boot ID; ownership lookup reads procfs and cgroup membership. It does not write `rp_filter`, forwarding, `accept_ra`, physical-interface settings or cgroup membership. The used wireguard TUN and netlink paths perform descriptor/ioctl/netlink operations; their sysfs fallback is a read. Profile output exists only in the separate acceptance build and targets its requested profile file.

The installed-service test logs the actual systemd/kernel versions on all three Linux runners. Inside the disposable network namespace it sets only `default.disable_ipv6=1`, leaves existing physical IPv6 intact, and requires the service log to prove the owned TUN changed from 1 to 0. It compares 15 global/default/physical settings before and after operation. The fault build additionally attempts ten write opens **inside the real Engine**, without writing any bytes: the TUN knob must open, and IPv4 forwarding/rp_filter, IPv6 all/default/loopback knobs, sysfs and cgroup paths must return read-only. The product build proves the actual write through start/restart. Capture checks resolve the current TUN by its ownership alias rather than incorrectly assuming a fixed Linux interface name. Hosted results on the new head remain required; the source comparison is not a substitute for those runs.
