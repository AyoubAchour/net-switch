# M4: native service contracts, first part

2026-10-22. This is the first reviewable part of the native-contracts PR in the M4 plan. Control's production cutover is still separate.

For the current child process model and watchdog, see [native supervision](m4-native-supervisor.md). The in-process stall evidence below is the earlier design evidence.

## Scope

The `m4_native` build uses the native runtime through the installed `netswitch-engine service` entrypoint and Ctl cleanup. Ordinary builds retain the M2 stand-in until the Control cutover. Selection is compile-time; there is no runtime fallback. The temporary tag goes away at cutover.

The native service shares runtime construction, authenticated transport and cleanup with standalone acceptance. Native ownership locks remain the exclusion boundary. The service supplies readiness and resume notifications and serializes epoch/revision history into one durable record. A restarted engine reports no loaded revision until start; an in-progress start does not report a loaded policy before capture succeeds. Old stand-in state is rejected here, pending the separately reviewed migration.

SCM and command exits retain the direct native outcome: clean adapter loss is 3, ordinary failure is 1, and an unrecovered Go panic remains 2. Joined cleanup errors cannot inherit the clean-loss code. Service status exposes the main exit separately from the final outcome. A final clean outcome requires a matching successful recovery result; a recovery failure becomes failure 1. Recovery captures the instance under the same native ownership lock, then writes its result after all closes, including the lock release. Each instance has its own outcome file, so an old recovery cannot overwrite a replacement service's result. Control's terminal handling and restart budget are described in [the production cutover](m4-production-cutover.md).

Native history uses one atomic replacement with file and directory sync, without an unread backup. After a failed sync following replacement, the next operation preserves the durable epoch/revision floor. An unacknowledged epoch may be retried, but an acknowledged epoch cannot be reused. Status publishes adapter loss as stopping immediately, includes a bounded last error, and retains failures until a new start.

A temporary-file regression also reproduced Windows replacement failing while a status reader holds the destination open, including with delete sharing. Native state replacement retries only sharing/access conflicts for at most 250 ms; permanent errors still fail. The journal observer never repairs or writes the journal and waits for the final recovery result before reading its checkpoint, so the diagnostic cannot block or truncate the cleanup it measures.

## Totals

The maximum-cardinality test admits and closes 65,536 distinct 512-byte app identities across 255 lines. The old single reply exceeds 1 MiB by more than thirty times. This is measured from real flow-table accounting, with no fabricated oversized diagnostic field.

`totals {cursor}` now returns `{engineInstanceId, apps, lines, count, receipt, cursor?}`. Each counter includes `{up, down, generation}` and is cumulative within that generation. Pages use a 512 KiB encoded budget, including space for escaping and the reply envelope. The first call freezes the counters, including closed flows; later pages read that same snapshot. `count` is the total number of app and line entries. A missing cursor means completion. Both existing native acceptance clients consume and validate the full sequence. The 65,536-app/255-line fixture now takes 70 pages; its largest measured reply is 523,543 bytes.

Totals share the flow snapshots' four-slot, ten-second and byte reservations. Aggregation memory is reserved before copying. A completed snapshot remains reserved until acknowledgement or expiry. An exhausted snapshot budget or expired cursor is an error; no accounting is truncated or evicted. A caller must discard an incomplete poll. `stats` remains separate and bounded.

The retained set is capped at 65,536 app identities and 65,536 line identities. After consuming every page, Control must durably commit its per-instance, per-generation byte high-water marks, then send fenced `ackTotals {opId, receipt}`. Acknowledgement retires only idle entries whose generation and byte values still match the snapshot. Configured lines retain their cumulative counters; retired lines can be removed. New traffic, partial reads, expired/foreign receipts and late overlapping acknowledgements cannot discard unread bytes. A repeated identity receives a new generation after retirement. A lost acknowledgement is retried with the same operation ID; if it expired, another full read is safe because Control has already committed its high-water marks.

If Control falls behind and fills the retained set, existing identities keep forwarding. Admission of a new identity is refused with the separate accounting-capacity counter until space is acknowledged. This is the bounded, exact-accounting contract recorded in the spec; the production Control consumer is described in [the production cutover](m4-production-cutover.md). The acceptance clients consume in memory because they are test controllers, not durable usage stores.

Tests cover maximum cardinality, escaped IDs, completed-between-poll traffic, a flow closing after the first page, concurrent new traffic, partial/expired/foreign reads, overlapping acknowledgements, both TCP and UDP admission, line churn, shared snapshot budgets and controller fencing. A long churn test consumes all bytes from 102,400 distinct 512-byte identities with a retained limit of 1,024, without resetting the table. It checks exact independently generated bytes and live heap after forced GC: 244,768-byte baseline and 413,432-byte peak in the local run. Hosted fault builds separately fill both retained identity sets to 65,536 and time a complete read over the installed service connection while a held flow continues. That measurement must finish inside the unchanged ten-second snapshot lifetime.

## Installed service proof

`native-service-contracts.yml` runs Windows x64/ARM64, Ubuntu 24.04 x64/ARM64 and Ubuntu 26.04 x64. Each job builds and installs two native candidates in separate directories: one without fault hooks and one with `lifecycle_test`.

The suite records each binary's version/hash, checks the running service image and PID, and uses the real root/SYSTEM engine connection. It also verifies that another OS user is denied while the engine service is live. Tests exercise start/apply/status, stale/conflicting revisions, stable apply points, reattachment/fencing, old-flow closure with newer-flow survival, all totals pages, historical state after restart, graceful stop, lease expiry, actual service crashes and native Ctl/SCM/ExecStopPost cleanup. Capture and held traffic are established before any cleanup is credited.

The disposable account helper owns cleanup immediately after creation, including partial setup failures. Reuse requires the fixture's name/comment and an unprivileged identity: Linux checks UID/GID, private group, home and locked password; Windows checks the local account and direct/indirect group memberships before resetting its test password. The installed ACL case exercises reuse, still requires a real permission denial against the live service, and checks account removal after its subtest. Cleanup errors are reported. The Linux ACL-only account no longer starts a lingering user manager; session-test actors still do, and their cleanup stops that manager and its slice before deleting the account. Previously the callback discarded `userdel` errors, hiding the leftover until the second suite pass.

The first Windows validator then rejected a valid freshly created account. The incorrect check required the value `1` supplied to `NetUserAdd` to come back unchanged from `NetUserGetInfo`. The shared validator now accepts the non-admin summaries 0/1 and still rejects admin/unknown values, wrong identity/comment, disabled/non-normal accounts and any local membership other than BUILTIN Users. Actual token elevation and the live denial proof are unchanged. Success logs include the observed summary, flags and group SIDs; rejection logs include the failing account properties. On `b49eccef`, Ubuntu 24.04 [x64](https://github.com/AyoubAchour/net-switch/actions/runs/39872191497/job/120149050453) and [ARM64](https://github.com/AyoubAchour/net-switch/actions/runs/39872191497/job/120149050376) both proved account reuse, live-service denial and removal in the product and fault passes. Windows asserts the journal's persistent WFP sublayer and three filters exist before killing the service, then waits for their removal and journal retirement. The explicit Ctl case disables automatic recovery, kills the service, proves those leftovers still exist, and only then runs cleanup. Linux proves its journaled selection rules similarly. A crash reported as clean 0 or adapter loss 3 fails. Separate injected exit-3 cases pass through the real manager, with both successful recovery and a recorded recovery failure.

The build without fault hooks is given an arm file and must continue forwarding without producing a hit record. The installed fault build has two observations:

- **Forwarding-only stall:** stop the real TUN read pump after it receives a packet. Observe for at least 22 seconds while renewal/version rounds still answer within three seconds. Require no delivery or reset before the client OS gives up. Verify capture still exists, release the fault, and require a fresh connection to work within ten seconds of release.
- **Whole-service stall:** suspend the actual service process for at least 35 seconds. Require the same no-delivery/no-reset condition until OS give-up and IPC silence while SCM/systemd reports the same process running. Verify capture still exists past the 30-second lease. These tests record `M4_STALL` evidence and `M4_PROGRESS` stats before, during and after the read-pump stall. This injection observes the read-pump domain only; it does not prove write-path or network-stack stall detection. The whole-service case records the last available counters and that stats become unavailable while suspended. These are observations, not a watchdog detector or a claim that native recovery already meets M2's guarantee. The coordinator reviews the hosted results before detector design. A separate watchdog process requires an architecture decision before implementation.

## First hosted failures and diagnosis

In run 39843807971, Linux ARM attached at 20:01:55 UTC; systemd deactivated the engine successfully at 20:02:26. The denial probe did not run until 20:02:36. Creating its OS user took longer than the 30-second lease, and this test client had no renewal loop. Ubuntu 26.04 x64 reproduced the same failure. The harness now renews while attached, stops and joins that loop before fencing/stop/suspension, and leaves the other-user denial requirement unchanged.

Windows was already ready: focused hosted diagnostic run 39847601708 recorded `ready-callback-end` at 20:29:21.682 UTC. Its epoch stayed zero because hello never completed. The shared M2 IPC dialer writes an impersonation primer byte before JSON; the native transport authenticates the SYSTEM process directly and does not consume that byte. The native decoder rejected it, then the RPC reader discarded the uncorrelated error and waited for the six-minute test deadline. A pure regression reproduced that misleading timeout before the fix. Native dialing now omits the M2 primer while retaining the SCM process check, and RPC surfaces a protocol rejection immediately. Attach has a specific ten-second diagnostic deadline, with service startup/outcome evidence on failure. Teardown explicitly stops the native service before uninstalling it.

## ARM stall result and further measurement

At head `886b220a`, run 39856819110, Windows ARM job 120097049942 passed the product build and both real cleanup paths. The fault build read all 131,072 accounting entries in 83 pages in 755.9 ms. Both exit-3 cases passed: `Cleanup:failed` with `hosted recovery failure before OS cleanup` belongs to the intentionally failing recovery case, not an unexpected cleanup failure.

The read-pump stall failed after 21.58 s with Winsock error 10060 (`WSAETIMEDOUT`). Whole-process suspension failed after 23.60 s, including the two-second IPC timeout before sending data. Those are native socket failures, not Go's `os.ErrDeadlineExceeded` polling errors. The old observation returned immediately and therefore proved neither survival through the full windows nor the post-fault fate of those streams. It did not complete the 35-second whole-service observation. The approximately equal times after sending data point to retransmission exhaustion, but the old log has no client retransmission counts or actual socket settings to prove that cause.

The diagnostic at `973cc72a` kept flow loss a test failure while collecting evidence through 22/35 seconds and release/cleanup. A separate 35-second quiet-stream control exercises the same one-second read deadlines with forwarding live. Windows reads the real client's keepalive, send/receive timeout and retransmission settings without changing them; `SIO_TCP_INFO` samples established state, unacknowledged bytes, retransmitted bytes and timeout episodes. Query cost is measured before injecting the fault, and sampling is every five seconds plus fault transitions, not per packet. Linux's Unix relay is explicitly labelled as such, not represented as the namespace TCP socket.

`M4_FLOW` records the first non-deadline event with elapsed time and errno, and the old stream after release. `M4_RECOVERY` measures a fresh connection from the release/resume action, before inspecting the old stream; it uses QPC on Windows to avoid coarse timer readings. No TCP setting, stall duration, lease limit or detector threshold is increased. The detector and process model remain unchanged.

Native socket references: [TCP_INFO_v0](https://learn.microsoft.com/en-us/windows/win32/api/mstcpip/ns-mstcpip-tcp_info_v0), [SIO_TCP_INFO](https://learn.microsoft.com/en-us/windows/win32/winsock/sio-tcp-info), [TCP socket options](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-tcp-socket-options).

The focused runs at `973cc72a` confirmed retransmission exhaustion: [ARM64 run 39860215642](https://github.com/AyoubAchour/net-switch/actions/runs/39860215642) and [x64 run 39860220499](https://github.com/AyoubAchour/net-switch/actions/runs/39860220499). Both quiet-stream controls survived 35 one-second polling deadlines. Actual keepalive settings were 15-second idle, 15-second interval and nine probes, with no socket receive/send timeout. x64 reported `TCP_MAXRTMS=18900`; ARM64 reported zero (the OS default). The established clients accumulated retransmissions with bytes still unacknowledged, then changed from TCP state 4 (ESTABLISHED) to 0 (CLOSED).

The read-pump cases retained responsive IPC (slowest round 0.566 ms ARM64, 1.382 ms x64) while native read/output counters stopped advancing. Both whole-process suspensions completed more than 35 seconds with capture still present; resuming let the expired lease clean up. The four diagnostic failures exposed an impossible held-flow expectation, corrected below. Sixteen preflight TCP queries cost 43–56 microseconds in total; periodic samples were below 1.8 ms, so this is not a per-packet timing diagnostic.

**Observation contract, clarified for PR 1a:** a TCP stream cannot outlive the client's retransmission limit during a complete forwarding stall, or preserve its netstack state across engine restart. OS give-up is therefore a measured fact, not a failure by itself. Windows accepts it only with `WSAETIMEDOUT`, ESTABLISHED-to-CLOSED transition, unacknowledged data and increases in both retransmitted bytes and timeout episodes. Data, RST, EOF, an unproved timeout or loss in the healthy deadline-control case still fails. Linux reports give-up as not observed within its window unless it has direct evidence; a relay EOF is not treated as an OS timeout. This is a bounded observation, not a claim of an infinite TCP lifetime.

Fresh flows must work after recovery, in one attempt under a shared deadline, with each dial and echo still capped at five seconds. The existing M2 gates stay intact: crash cleanup/direct traffic within 12 s, runnable-engine lease expiry within 42 s, hang cleanup within 28 s, and wanted-routing recovery within 70 s. PR 1a additionally checks 12 s from actual service crash to fresh direct traffic, and the 12 s post-resume lease-cleanup tail. The ten-second manual read-pump release check is not a detector. Fresh-flow recovery duration is recorded on each new run; the earlier diagnostic did not measure it separately, so no value is inferred from its case duration.

## Watchdog options — (e) recorded in the spec for the follow-up

The engine cannot detect or clean up its own whole-process suspension. The 35-second observations proved capture remained installed even after its lease expired. Control health alone also cannot identify a read-pump stall: version/renew kept answering in under 1.4 ms. A useful health signal must exercise forwarding, without depending on an internet line being up. Option (e) is recorded in spec §3.4, "The native engine keeps this separation (decided 2026-10-23)". It lands in the follow-up; no option below is built in this PR. The comparison below preserves the reasons for that decision.

| Option | Control absent or hung | Who removes suspended-engine capture | Fail-open time and cost |
| --- | --- | --- | --- |
| **(a) Control health + service-manager termination** | A runnable engine can expire its lease within 42 s, but this misses the 28 s hang gate. If Engine also hangs, there is no independent deadline. | Control verifies/pins the service instance, forces termination, then SCM recovery or systemd `ExecStopPost` runs journal cleanup. Control alone decides whether to restart. | With Control healthy, target the 28 s hang gate. Reuses privileged Control; no new process. Control load can delay probes or falsely time them out. Version-only probes miss the observed forwarding stall. |
| **(b) Minimal separate watchdog** | Independent of both Control and Engine; can fail open when both are hung. Its availability must be established before capture is enabled, with a recovery policy for its own crash. | Watchdog requests verified forced termination and completion of existing journal cleanup. It must not delete routes while a suspended engine still owns the lifetime lock. | Target detection plus termination/cleanup within 28 s. Adds a SYSTEM/root process, authenticated bounded messages, installation/update ownership and another lifetime to supervise. A starved watchdog or stale heartbeat can cause false positives. |
| **(c) Platform watchdogs** | Linux PID 1 can act with both app services hung. Windows SCM has no equivalent running-service heartbeat deadline. | Linux `WatchdogSec` expiry causes forced termination, then `ExecStopPost`; on Windows, existing SCM actions only help after the process stops/fails. | Linux can target 28 s using existing privileged PID 1 and `NotifyAccess=main`. Bound forced termination and core-dump waits instead of relying on graceful exit. CPU pressure can delay notifications; unrelated heartbeat goroutines miss forwarding stalls. Windows alone has no hang bound. |
| **(d) Independent protection plus Control** | Covers Control absence/hang on both OSes when Linux uses (c) and Windows uses (b). Control remains an optional earlier detector and owns restart/backoff/latch policy. | One independent supervisor terminates the verified instance; existing recovery removes capture. Concurrent Control decisions must use the same instance fencing and cleanup lock. | Target the same 28 s gate. More coordination and two platform implementations, but no extra Linux daemon and only a small Windows privileged component. Shared health policy prevents contradictory timers. |
| **(e) Engine service as supervisor; native child** | A runnable host supervises the child independently of Control, as M2 does. Optional Linux `WatchdogSec` protects the host itself. | Host terminates its verified child, waits for exit and lock release, then performs existing journal cleanup. The service manager handles host death. | Target the same 28 s gate. Reuses the installed Engine service and M2 supervision pattern, but adds a native-child launch/IPC boundary. A hung host needs the independent protection discussed below. |

All alternatives need the same load discipline: bounded private forwarding checks with M2's three-second probe deadline and roughly twenty seconds of continuous failures, healthy results resetting that window, and the existing awake-time/resume rules. Idle byte counters are not a failure signal. Do not let a renewal goroutine prove forwarding health. Under the 28 s gate, twenty seconds of detection leaves at most eight for termination and confirmed cleanup; this is a budget to prove under load, not a new promised timing. Process restart is separate: normal direct internet must work even if routing cannot restart. No watcher may restart routing without Control's durable intent or bypass its failure budget.

### Comparing (e) with (d)

Under (e), the existing Engine service becomes the monitor and the native child owns forwarding. It runs one child lifetime, performs bounded private forwarding checks, and exits with the final outcome after that child ends and cleanup completes. Control still owns every restart, backoff and latch; the host does not silently respawn children. This is a proposal for the follow-up PR. PR 1a can merge with its current in-process hosting following review and green checks.

| Concern | (d): platform protection plus Control | (e): supervisor host plus native child |
| --- | --- | --- |
| Control absent/hung; child forwarding hung | Linux PID 1 or the Windows watcher acts independently. Forwarding-qualified heartbeats are essential. | The host remains runnable when the child is suspended/deadlocked, so its private checks can expire and kill the child. Same three-second probes, twenty-second failure window and 28 s fail-open target; inheritance alone is not a detector. |
| Capture removal and ownership | Terminate the Engine service process; its registrar/TUN handles close. Recovery then takes the released native lock and removes journaled leftovers. | Terminate the verified child, join its exit and registrar teardown, then acquire that same native lock for cleanup. The child is the sole native lifetime-lock owner. The host must not retain M2's `engine.lock` while launching or supervising it. |
| Monitor itself hangs | A hung Windows watcher plus hung Engine and absent Control has no remaining observer. Linux relies on PID 1 remaining runnable. | A hung host plus hung child and absent Control has the same Windows gap. Host **death** triggers its job/Pdeathsig/cgroup guards; host **hang** does not. A runnable child can still expire its genuine Control lease; the host must never fabricate renewals. Linux can watchdog the host's supervision progress, including completed probe timeouts. |
| Steady processes while routing | Linux: **2** (Control, Engine). Windows: **4** (Control, Engine, registrar, watcher). | Linux: **3** (Control, host, child). Windows: **4** (Control, host, child, registrar). Thus one extra Linux process and the same Windows count as (d). Desktop, ordinary workers and transient cleanup commands are excluded from both counts. |
| Privileged surface | One new installed SYSTEM service on Windows, with its own ACL, installation/update/recovery state and authenticated engine relationship. No additional Linux process. | No new installed service, but host and child are still SYSTEM/root processes. Adds a private bootstrap/control channel and possibly a relay; the service must not accept arbitrary executable paths or commands. Existing installation trust can cover both modes of the signed engine binary. |
| Resource and review cost | Keeps PR 1a's IPC identity, registrar placement and direct exit mapping. Requires a Windows watcher lifecycle and a Linux notification policy. | Shares supervision logic across OSes but changes IPC/identity, readiness, exit propagation and Windows job placement. Higher contract-review cost, even though the process guard itself is small. |

Neither model can promise fail-open if its last independent monitor and forwarding process both hang. With a healthy monitor, both must prove detection **plus** forced termination **plus** cleanup within 28 s, including when Control is absent. `TerminateProcess` is asynchronous: requesting a kill is not proof of exit or lock release. Host-side Linux termination must target the child, not kill the host's own entire service cgroup; systemd's `KillMode=mixed` remains the backstop for unit termination. [Windows termination](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [systemd cgroup termination](https://www.freedesktop.org/software/systemd/man/255/systemd.kill.html).

Both pay for the same private probe cadence. Under (e), forwarding packets stay entirely in the child; a host IPC relay adds a hop only to Control traffic. That relay and logging must have global buffer bounds and must not block health checks or exit handling. Re-test the full totals read against its ten-second lifetime under load. Each extra process adds its own Go heap, stacks, handles and scheduling; exact memory/CPU costs for these proposed roles are **unmeasured**, so no MiB saving is claimed. Host runtime limits must not accidentally throttle the child through inherited environment variables.

**What PR 1a would change under (e):**

- **IPC and PID assertions.** I prefer the host retaining the public native endpoint and transparently relaying to a private child channel. Keep native framing and ACLs, including the absence of the M2 primer. Replace `service_pid == protocol_pid` with two proofs: public IPC peer PID equals the SCM/systemd host PID; reported engine PID equals the verified guarded child. Do not relabel the host as the forwarding engine. Direct child IPC avoids the relay, but Windows then needs a host-authenticated binding to the child's pinned identity: `DialNativeEngine` currently rejects a server PID different from SCM's, and parent PID or SYSTEM identity alone is not a replacement for that check. [Current dialer](../internal/localipc/ipc_windows.go).
- **Readiness, leases and state.** Report service readiness only after the expected child has opened its authenticated channel, recovered ownership and initialized durable state, with health supervision armed. The child retains the sole protocol epoch/revision/lease authority; relay real Control renewals and terminal acknowledgements end to end. Forward power/resume notifications with the existing awake-time rules. A hung proxy must not extend the child's lease. The current standalone `run` mode lacks the service-state callbacks, so launching it unchanged is insufficient. [Current native host](../internal/lifecycle/native_engine.go).
- **Registrar placement is a real Windows change.** The registrar already has an atomic `JOB_LIST` launch, a one-process kill-on-close job and UI restrictions. It would inherit the new outer child job, but Microsoft documents that UI-limited jobs cannot simply be nested. Resolve this before cutover: either preserve its separate job through explicitly reviewed breakaway, or let the host broker it as a sibling with separate guarded ownership. Breakaway permission applies to the job, not an executable allowlist; the sibling design adds handle-transfer logic. Do not drop UI restrictions or permit unguarded registrar lifetime to make startup pass. Test host/child death at every creation/assignment/resume boundary. [Registrar implementation](../internal/wintun/registrar_windows.go), [nested-job restrictions](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).
- **Exit outcomes.** `cmd.Wait()` returns an `exec.ExitError`, which the current service exit mapper would classify as 1. The host must explicitly propagate an unforced, completed child exit 3 only after its own cleanup and guard closes also succeed; then SCM/systemd exposes 3 for that child instance. Cleanup errors, forced termination and crashes remain failures, with the raw child result retained. Unexpected child exit 0 cannot become a clean routing-off result. The host must finish and exit, not hide child failure behind a restart loop. [Exit mapping](../internal/service/service.go).
- **Installed proofs.** Keep both binaries' hashes, public/child identity checks, other-user denial, full paging and durable fencing. Add child read-pump/whole-child stalls with Control absent, host crash, host suspension, host+child suspension, startup death before readiness, nested/breakaway registrar containment, slow relay/log readers, and child 3 → host → manager tests including failed cleanup. Keep persistent WFP/rule preconditions and the 28 s hang/12 s crash/42 s lease/70 s recovery gates. A separate supervisor lock, if needed, must never be confused with the child's native ownership lock.

**Actual M2 reuse:** the three `child*.go` files total **101 lines**, not a ready-made native supervisor. The Linux launch mechanism (`Pdeathsig=SIGKILL`, inherited service cgroup) and generic process/pipe operations are reusable; Pdeathsig follows the creating **thread**, not suspension, and credential/file-capability transitions need review. Windows can retain the kill-on-close concept, suspended launch and failure cleanup, but its current create-then-assign sequence has a pre-assignment orphan window (a suspended child, before forwarding starts) and its release callback discards close errors. Native hosting should use atomic job assignment and preserve those errors; registrar placement prevents claiming unchanged Windows launch code. [Child launcher](../internal/lifecycle/child.go), [parent-death semantics](https://www.man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html), [atomic job attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

The 37-line `healthWatch` window, power-pause rules, service-manager boundary and native journal recovery can keep their logic. The adapter-specific command line, sing-box return type/config/HTTP health implementation and M2 host-owned protocol/lock cannot be carried across unchanged. `ChildEnvironment` already strips notification/socket-activation variables; native launch must also isolate any host watchdog/runtime settings. The gain is reuse of proven mechanisms and test scenarios, not retaining the adapter or wrapping it under another name.

For planning, excluding the private forwarding probe that **both** need, I would budget roughly **1–2k changed lines for (d)** and **2–3.5k for (e)** including focused tests. These are estimates, not measured patch sizes. For (e), review child/registrar containment separately from hosting/protocol/outcome integration; if it exceeds the review limit, land sequential PRs from main rather than a branch stack.

**Recommendation, now recorded in the spec: (e), with host-owned public IPC and Linux watchdog protection of the host, for the follow-up.** It restores M2's clear separation between supervision and forwarding, keeps one supervision policy across OSes, and avoids a third installed Windows service while using the same Windows process count as (d). I would accept the extra Linux process and larger contract rewrite for that operational model. This is not the smaller immediate patch: (d) wins on Linux footprint and preserves more of PR 1a unchanged. The Windows registrar/atomic-launch work is a prerequisite, not a waived check. Neither proposal fixes a simultaneous hung Windows monitor and forwarding process without another independent mechanism. No hosting model is implemented here. PR 1a can merge on its current hosting following review and green checks.

## Linux stopped-status retention

On `cb9b36c6`, all three Linux runners failed the clean-stop assertion: Ubuntu 24.04 [x64](https://github.com/AyoubAchour/net-switch/actions/runs/39865514838/job/120127087762) and [ARM64](https://github.com/AyoubAchour/net-switch/actions/runs/39865514838/job/120127087899) used systemd 255.4; Ubuntu 26.04 [x64](https://github.com/AyoubAchour/net-switch/actions/runs/39865514838/job/120127087776) used 259.5. Each journal reports successful deactivation, and each matching recovery record is complete. Both Windows jobs passed. This is a status-retention defect, not evidence of failed engine cleanup.

The bridge relied on a later `systemctl show` retaining `ExecMainCode` and `ExecMainStatus`. Systemd documents that collecting an unreferenced inactive unit discards these results; a later lookup loads a fresh unit. Waiting longer cannot restore them. The old diagnostic omitted the raw properties, so collection is inferred from the logs and documented lifecycle, rather than directly captured in that run. [Unit collection](https://www.freedesktop.org/software/systemd/man/255/systemd.unit.html#Unit%20Garbage%20Collection).

The existing `ExecStopPost` cleanup now retains systemd's actual `EXIT_CODE`, `EXIT_STATUS` and `SERVICE_RESULT` in the native instance's outcome. The service records its `INVOCATION_ID` at startup; cleanup must match it before saving manager evidence. Explicit Ctl cleanup preserves that evidence. A foreign startup cannot attach a new main exit to old cleanup. Only a stopped, freshly loaded manager state can fall back to this record; live manager evidence and signal deaths are never replaced by a clean exit. Successful cleanup alone remains insufficient. [Manager-provided exit variables and invocation identity](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#%24SERVICE_RESULT), [manager source](https://github.com/systemd/systemd/blob/v255/src/core/service.c).

Status and cleanup logs now expose raw manager code/status/invocation and the retained-result source. Pure regressions cover clean 0, exit 3, signals (including systemd-successful SIGTERM), missing/corrupt evidence, pending/failed recovery and foreign invocations. The installed proof explicitly waits for the stopped unit to disappear from `list-units`, requires the freshly loaded raw status to be empty/zero, then requires retained clean exit 0. On `87d79db5`, [Ubuntu ARM64 job 120140080282](https://github.com/AyoubAchour/net-switch/actions/runs/39869511309/job/120140080282) confirmed collection and retained `exited/0/success` with the matching invocation in both suite passes; its later failure was the account-helper cleanup issue above. No service was run locally.

## Linux installed-service sysctl boundary

The installed unit correctly made `/proc/sys` read-only. The native engine nevertheless unconditionally wrote `disable_ipv6=0` for its newly created TUN; standalone acceptance had no such mount boundary. The native-only unit now keeps `ProtectKernelTunables=yes`, permits `/proc/sys/net/ipv6/conf`, and makes its `all`, `default` and `lo` subdirectories read-only again. Control and the stand-in unit receive no exception. The engine verifies the TUN's index/name/ownership alias, reads the current value and writes only when it inherited `1`.

This is the smallest static parent that can contain the runtime-created device. A narrower **existing** per-device file can be made writable, but our random per-instance path does not exist when systemd constructs the mount namespace. Without `-` startup fails; with `-` the missing mount is skipped, not added when the device appears. Both [systemd 255's path rules](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#ReadWritePaths=) and [259's rules](https://www.freedesktop.org/software/systemd/man/259/systemd.exec.html#ReadWritePaths=) support nested writable/read-only mounts. Their [255](https://github.com/systemd/systemd/blob/v255/src/core/namespace.c) and [259](https://github.com/systemd/systemd/blob/v259/src/core/namespace.c) implementations apply the `/proc/sys` protection as a mount and skip missing optional entries at setup. No extra capability, helper process or global sysctl change is introduced. The exception necessarily exposes other per-interface IPv6 knobs to Engine; global/default knobs, IPv4, sysfs and cgroups remain read-only. A per-device sandbox would require a different creation/hosting arrangement.

Avoiding the write is safe when the inherited value is already zero, which the engine now does. It is insufficient when a physical line has usable IPv6 but newly created devices inherit `disable_ipv6=1`. The kernel copies the namespace defaults into new IPv6 devices, and rejects disabled devices for IPv6 address configuration. The netlink IPv6 link setter accepts token/address-generation changes, not `IFLA_INET6_CONF` writes, in both [Linux 6.8](https://github.com/torvalds/linux/blob/v6.8/net/ipv6/addrconf.c) and [7.0](https://github.com/torvalds/linux/blob/v7.0/net/ipv6/addrconf.c). Raising the link or changing its address-generation mode therefore cannot replace this sysctl write.

Write-site audit: `enableIPv6` is the only product `/proc/sys` or sysfs writer in the native Linux engine. The engine reads `ping_group_range` and the boot ID; ownership lookup reads procfs and cgroup membership. It does not write `rp_filter`, forwarding, `accept_ra`, physical-interface settings or cgroup membership. The used wireguard TUN and netlink paths perform descriptor/ioctl/netlink operations; their sysfs fallback is a read. Profile output exists only in the separate acceptance build and targets its requested profile file.

The installed-service test logs the actual systemd/kernel versions on all three Linux runners. Inside the disposable network namespace it sets only `default.disable_ipv6=1`, leaves existing physical IPv6 intact, and requires the service log to prove the owned TUN changed from 1 to 0. It compares 15 global/default/physical settings before and after operation. The fault build additionally attempts ten write opens **inside the real Engine**, without writing any bytes: the TUN knob must open, and IPv4 forwarding/rp_filter, IPv6 all/default/loopback knobs, sysfs and cgroup paths must return read-only. The product build proves the actual write through start/restart. Capture checks resolve the current TUN by its ownership alias rather than incorrectly assuming a fixed Linux interface name. Hosted results on the new head remain required; the source comparison is not a substitute for those runs.
